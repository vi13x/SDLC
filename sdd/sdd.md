## 1. Введение

### 1.1 Назначение документа

Определить устройство приложения на основе [SRS](../srs/srs.md), распределить ответственность модулей и подготовить реализацию. Документ предназначен разработчику и проверяющему; заказчик рассматривает функции, сроки и бюджет.

### 1.2 Область применения

Локальный дневник нескольких автомобилей для одного пользователя: ТО, пробег, заправки, полисы, напоминания, расходы, копии. CR-01 предлагает PDF-отчёт. Сервер, GPS, OBD и облако вне MVP.

### 1.3 Определения

SDD — описание проектирования; ADR — запись архитектурного решения; DTO — данные для передачи между слоями; ТО — техническое обслуживание; CR — запрос изменения.

### 1.4 Ссылки

[Шаблон SDD](sdd-template.md), [план и смета](../docs/lab4-plan.md), [изменение SRS](../srs/lab4-change-request.md).

### 1.5 Обзор документа

Раздел 2 задаёт точки зрения, раздел 3 — проверяемые системные требования и сценарии, раздел 4 — ADR, раздел 5 — ссылки на планы.

## 2. Обзор дизайна

### 2.1 Задачи стейкхолдеров

Владелец хочет хранить историю и не пропускать ТО. Разработчик должен обеспечить согласованность данных и тестируемость. Заказчик ограничивает сроки и бюджет; план P2 пока ожидает подтверждения.

### 2.2 Выбранные точки зрения

#### 2.2.1 Контекст

Пользователь взаимодействует с Qt Widgets. Приложение использует файлы SQLite и PDF на Windows, не обращается к внешним API.

#### 2.2.2 Композиция

UI (окна и формы), Application Services (сценарии), Domain (правила), Repositories (SQLite), ExportService (PDF), BackupService (копии).

#### 2.2.3 Логическое представление

VehicleService управляет карточками; MaintenanceService — ТО и расходниками; ReminderService — сроками; FuelService — заправками; InsuranceService — полисами; ExpenseService — суммами.

#### 2.2.4 Физическое представление

Один исполняемый файл, библиотеки Qt, плагин SQLite, локальная база пользователя. PDF и копия записываются по выбранному пути.

#### 2.2.5 Структура

src/ui, src/application, src/domain, src/storage, src/export; tests/domain и tests/storage. Основные классы интерфейсов: IVehicleRepository, IMaintenanceRepository, IClock, IReportExporter.

#### 2.2.6 Зависимости

UI вызывает сервисы; сервисы используют доменные правила и интерфейсы репозиториев. SQLite реализует интерфейсы. Domain не зависит от QWidget и файлов БД. PDF зависит от DTO отчёта; расходы зависят от сохранённых ТО, заправок и полисов.

#### 2.2.7 Информация

Таблицы vehicles, maintenance, maintenance_items, service_plans, refuels, policies, settings, schema_version. Каждая запись истории имеет vehicle_id с внешним ключом. Деньги хранятся в копейках (64-битное целое), литры — в тысячных долях литра. Даты — ISO YYYY-MM-DD. Индексы: vehicle_id/date. Изменение записи и пересчёт текущего пробега выполняются в одной транзакции.

#### 2.2.8 Интерфейс

Формы из [мокапов](../srs/diagrams/mockups) передают валидированные DTO. Repository возвращает результат или ошибку; UI показывает понятное сообщение, сохраняя введённые данные. ExportService принимает vehicleId, periodFrom, periodTo и targetPath.

#### 2.2.9 Взаимодействие

Добавление ТО: форма → проверка полей → транзакция сохранения → пересчёт пробега и планов → обновление таблицы. Ошибка откатывает транзакцию. Экспорт: выбор периода → снимок данных → итоги → временный PDF → атомарное завершение записи.

#### 2.2.10 Алгоритм

ТО наступает при today >= dueDate ИЛИ mileage >= dueMileage по заданным пределам. Превышение — просрочка; равенство без другого превышения — срок наступил. Полис действует включительно по дату окончания. Для тестов текущая дата задаётся через IClock.

#### 2.2.11 Динамика состояний

План ТО: запланирован → скоро → срок наступил → просрочен → выполнен. Выполнение требует подтверждения. Полис: будущий → действует → истекает → истёк. Состояния вычисляются из данных, а не вводятся пользователем вручную.

#### 2.2.12 Параллелизм

UI работает в главном потоке. PDF и создание копии выполняются в рабочем потоке со своим соединением SQLite. Объекты соединения не передаются между потоками. Сохранение сериализуется; UI получает результат через queued signals.

#### 2.2.13 Паттерны

Repository изолирует хранилище, Service Layer — пользовательские сценарии, Dependency Injection — часы и репозитории для тестов. Сетевые микросервисы для локального MVP не нужны.

#### 2.2.14 Развёртывание

C++17, Qt 6 Widgets/SQL/PrintSupport, SQLite, CMake. План поставки: cmake -S . -B build; cmake --build build --config Release; cmake --install build --prefix package; сбор необходимых DLL и платформенного плагина Qt. Эти команды описывают будущую сборку, исполняемого проекта в данной ветке пока нет. База создаётся в QStandardPaths::AppLocalDataLocation. Обновление сначала резервирует и мигрирует базу.

#### 2.2.15 Ресурсы

Windows 10/11 x64, 2 ядра, 8 ГБ ОЗУ, SSD, 10 000 записей для контрольных замеров. План команды и бюджета — в docs/lab4-plan.md.

## 3. Проектные представления

| Системное требование | Связь с SRS | Реализация и проверка |
|---|---|---|
| SYS-FUNC-001 | FUNC-001–004, 006, 008 | CRUD через сервисы и репозитории; проверить сохранение и связи автомобилей |
| SYS-FUNC-002 | FUNC-005, 009 | Чистая функция статуса по дате и пробегу; граничные тесты равенства и превышения |
| SYS-FUNC-003 | FUNC-007, 011 (proposed) | ExpenseService и PDF по одному DTO; сравнить суммы и выбранный период |
| SYS-NFR-001 | NFR-001–004 | Транзакции, фоновые длительные операции; 100 замеров на 10 000 записей |
| SYS-SEC-001 | SEC-001–003 | Параметризованный SQL, каталог пользователя, подтверждение удаления, проверка копии |
| SYS-EXT-001 | EXT-001–003 | Справочник работ, раздельные слои, версионированные миграции с тестом сохранности |
| SYS-DEP-001 | DEP-001–003 | Пакет Qt/SQLite; проверка запуска на чистой Windows и сохранения базы при обновлении |

Здесь FUNC/NFR/SEC/EXT/DEP обозначают полный префикс REQ соответствующего требования. Реализационные проверки имеют статус Planned. Критерии экспорта: корректная кириллица, многостраничный документ, пустой период, совпадение итогов с историей и отсутствие изменения БД при отмене.
